## 复现及验收方法

在独立 Linux 克隆中用数值学号设置本地 Git `user.name`，准备 Git、Docker 和 Compose v2。以下命令在仓库根目录运行。构建候选和报告修复均在本轮目录中进行。服务端口只绑定本机，DRAFT 容器持有本轮专用环境的 Docker socket。

```bash
python3 run_e11e12.py test
python3 run_e11e12.py build
python3 run_e11e12.py prepare
python3 labs/e13e14/prepare_a14.py
export E14_ROOT="$PWD" E14_IMAGE=course-e11e12:241880223
export E14_UID="$(id -u)" E14_GID="$(id -g)"
export COMPOSE_FILE=labs/e13e14/compose.yaml COMPOSE_PROJECT_NAME=a14-e14
docker compose config --quiet
docker compose up -d --wait
docker compose ps --format json
python3 labs/e13e14/orchestrate.py --request data/integration-sample/e12.json --out work/e14-fixed-review
python3 labs/e13e14/orchestrate.py --request data/e13-a14/e12.json --out work/e14-a14-review
docker compose logs --no-color > work/e14-review-services.log
python3 labs/e13e14/scan_runtime_logs.py work/e14-fixed-review work/e14-a14-review work/e14-review-services.log
docker compose down
```

运行按 DRAFT、BuildChecker 基线全量、EChecker 增量、MDFixer、BuildChecker 动态复验排列。BuildChecker 另外对目标版本作全量对照。每轮保留同一 job/trace、五阶段报告字节哈希、补丁哈希、重新构建的程序输出和四个服务各自的日志。受控故障使用同一项目的新请求，构建时限设为 0.01 秒。核对 DRAFT 超时、失败记录、客户端进程状态与新任务恢复。CI 中有完整的正常、故障、恢复命令，并用 `verify_e14.py` 核验证据。

## 已知限制与回退

- 当前支持两份 C 源、显式 GNU Make 规则和可声明的头文件变更。BuildChecker 使用真实动态 trace。EChecker 沿用 GCC 依赖提取与保守缓存的教学实现。超出范围的项目需先提供适配和实测证据。
- 四个 HTTP 角色共用教学镜像和课程工作区，CI 的 B 角色来自课程参考实现。B14 实际服务和本轮镜像需联合验收。
- 回退时先保存本轮日志、请求、镜像 ID 和结果，再用 `docker compose down` 停止本轮 Compose 项目。切到双方认可的上一组提交与镜像，在新目录用原请求重跑，核对阶段及输出。E12 正式回执可作为回退核对依据，见 [E12 验收记录](../e11-e12/PR验收记录.md)。

发布前需同时完成实际配对 C1–C8、教师隐藏测试、阻断缺陷闭环、最终提交的必需 CI 与评审，以及用真实配对输入完成四服务和故障恢复。标签和发布说明由有权限的发布人固定到验收提交。
