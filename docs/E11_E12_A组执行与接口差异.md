# A14 E11–E12 执行与交接

## 当前可执行范围

`labs/e11e12/a_track.py` 接续 E8–E10 的受限 C/Make 教学实现，在 Linux 环境对两个完整 Git SHA 运行：BuildChecker 基线全量检查、基线图入缓存、EChecker 教学增量扫描、目标全量交叉核对、完整报告及 MD-only 报告导出。输出必须使用新的 `work/` 目录。当前支持 E8–E10 双目标样例及 A14 E3 的单目标显式规则项目；其他真实项目需先适配目标、规则、编译选项和行为验证。

```sh
python3 -m unittest discover -s labs/e11e12 -p 'test_*.py' -v
python3 labs/e11e12/a_track.py \
  --repo data/real-project \
  --base <40位基线SHA> --target <40位目标SHA> \
  --repository-url <真实仓库URL> \
  --configuration-id <锁定工具链与构建配置的ID> \
  --out work/e11-a-<本次唯一编号>
```

A14 已有 E3 连续真实提交可作组内第一轮验证，但它仍是课程维护的受控项目，并非外部项目验证：

```sh
python3 labs/e11e12/a_track.py \
  --repo . --project-path e3/fixtures/commits/project \
  --base 4445e4be50af6683b75017e7fa65c4f8212ea80e \
  --target 37fcadb1eced8d2504b1d5e0bd96f3b8091568b1 \
  --repository-url https://github.com/oVLVo11/DevOps_A14.git \
  --configuration-id a14-e3-linux-x86_64-gcc11-make43 \
  --out work/e11-a-e3-c0-c1-<本次唯一编号>
```

先在运行环境安装 E7 BuildChecker 所需的 `gcc`、`make`、`strace`、`git`。`baseline-full/` 和 `target-full/` 含原始 trace、Make 数据库、图与发现；`comparison.json` 要求对象目标的实际图、声明图、发现集合全部相同。`incremental-report.json` 记录刷新和复用目标。`handoff.json` 指向 `manifest.json` 中带哈希的全量图、增量图、完整报告和 `md.json`。交接时同时提供 `artifacts/`，不可只复制 URI。

`labs/e11e12/recheck.py` 接收目标提交、MD-only 报告、补丁 URI 与实际文件 SHA-256；先在独立克隆中应用补丁，再构建、运行程序并执行 BuildChecker 动态重检。它拒绝旧提交、配置不符、非 MD-only 报告、补丁摘要错误及非目标 Makefile 补丁。CI 使用 `fixtures/e3-c1-reference.patch` 演练这条 A 组复验路径；该补丁是 **A14 本地参考输入，不是 B14 实际候选**。实际联调必须替换为 B14 返回的原始补丁与 URI，并在 B14 DRAFT 环境中复验。

## 论文与证据边界

- BuildChecker（TSE）§4：clean build 的动态文件访问和 GNU Make 内部数据库建立执行—声明模型。保留原始证据，不以 `gcc -MM` 代替动态基线。
- EChecker（ISSTA 2024）§3：历史图、增量构建跟踪、预处理指令/文件/构建命令变化与图归并。当前 E8–E10 `scan` 仅通过 `gcc -MM` 和保守签名更新固定目标；它尚无增量系统调用图归并。目标全量运行只用于正确性对照，不可用本流程声称论文级性能收益。
- 报告按实际来源标注 `DYNAMIC_TRACE` 与 `STATIC_INFERENCE`。同一发现的 `finding_id` 跨提交稳定，完整报告保留 RD；交给 MDFixer 的 `md.json` 只含 MD。

## 与 B14 确认后才能正式跨组交接

双方 E2 `1.0` 契约的 `Graph.source` 与 `RecheckReport.source` 当前只允许 `MANUAL_FIXTURE`，真实图和重检不能如实通过这两个字段。用户选择先维持 1.0，因此导出包将真实来源写入图，并在 `handoff.json` 标为 `REPORT_READY_GRAPH_SOURCE_BLOCKED`。**MD-only 的 `Report` 与产物元数据可按 1.0 交接；真实图和重检不得声称已通过 B14 的严格内容校验。** 若将来双方决定扩充字段，需要覆盖图的 `DYNAMIC_TRACE`、`STATIC_INFERENCE`、`MAKE_DATABASE` 和重检的 `DYNAMIC_TRACE`，同步 schema、校验器、样例和版本决策。人工样例不改写成真实证据，真实图和重检也不伪装成人工样例。

还需双方确认真实 `repository_url`、base/target 完整 SHA、`configuration_id`、DRAFT `image_ref` 与构建命令、产物下载/权限、B14 REPAIR 接口及候选 `patch_uri`。A14 对补丁重检时保持目标 commit 为补丁基线 SHA，并用 `patch_uri` 标识工作树变化；重检须在同一配置下执行，最终由 B14 判定补丁是否接受。

## 提交验收

个人分支提交代码、测试、报告和 ADR；`work/` 原始证据单独归档。报告写明外层源码 SHA、项目提交 SHA、镜像身份、命令、原始目录、图与发现对照、MD-only 交接校验、B14 实际消费记录以及未完成的论文机制。固定样例通过不能代替真实项目、真实镜像或跨组联调。
